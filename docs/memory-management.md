# Similarity メモリ管理研究 — 直接アドレス参照・可変長断片の論理統合・空き領域再利用

- **整理日:** 2026-10-31
- **状態:** 研究・設計検討中。実装済み／性能証明済みではない。
- **対象:** 2026-10-29〜31頃の議論、および2026-10-30の大学教員との面談で得た論点
- **位置付け:** [2026-10-26の議事録](meetings/2026-10-26.md)の後に検討した**新しい方向性**。以前の「全データ固有ID・親子ID・16区間リング・中央ID表」を、そのまま現行の前提にはしない。過去案は議事録として保持する。

> **読む際の注意:** 「こう扱いたい」という**目標**と、「実際にこの方法で可能だと確認できた」という**結果**を区別する。以下のアドレス・範囲は図解用であり、Similarityの正式な言語構文ではない。

## 1. 研究の出発点

従来の検討では、すべてのデータに位置とは独立した固有IDを付与し、移動後もIDから位置を解決する方針を考えていた。

新たな問いは、**「そもそもすべてのデータに固有IDを付け、すべてのデータを移動可能にする必要があるのか？」**。

- アドレスはある時点の格納場所を直接指定できる。固定長データなど、複雑な間接参照を必要としない場合は**直接アドレス参照**を基本候補とする。
- 主要な課題は、特に**可変長データの伸長・縮小・解放**に集中しているのではないか。
- 通常のデータすべてに固有IDや位置変換表を付けるコストを避け、**必要な部分にだけ追加の管理情報を置く**方向を研究する。
- **注意:** アドレスは恒久的なオブジェクト同一性を保証しない。同じアドレスの解放・再利用時に古い参照が誤って新しいデータを指す問題、移動時の参照の扱いは別途解決が必要。

## 2. 固定長データと可変長データを分ける【方向性】

### 固定長データ

- **生存期間が適合する場合はスタック配置**を基本候補とし、直接アドレス参照する。
- 固定長という条件だけで必ずスタックに置けるわけではない。関数終了後まで生きるオブジェクト、任意順序で解放したいオブジェクトなどには別の扱いが必要。
- 固定長データのすべてに可変長データ用の断片管理情報を付与しない。

### 可変長データ

1. 隣接する領域が空いていれば**その場で伸長**する。
2. 隣が使用中で伸長できなければ、**別の空き領域へ追加部分を置く**。既存データ全体のコピーや再配置は原則避けたい。
3. 物理的に離れた断片は、**外部に保持したアドレス範囲の情報**で、論理的に一つの可変長データとして扱う。
4. 再び隣接した断片があり、**物理的にも論理的にも連続していれば**、範囲の管理情報を統合できる。

## 3. 断片を「使用時に一つとして読む」構想【核心・未実証】

リンクを1件ずつ辿る方式との違いは、**各断片の格納アドレスを外部に一覧として把握しておき、使用時に各アドレスへ直接アクセスし、論理順に地続きのデータとして読む**ことを目指す点。

説明例（範囲の終端は含めない）：

```text
物理配置
0x1000〜0x1004 : ABCD
0x1004〜...    : 別のデータ
0x5000〜0x5004 : EFGH
0x9000〜0x9004 : IJKL

先頭アドレス 0x1000 を手がかりに外部の管理情報を得る（例）
0x1000 → [
    (0x1000, 0x1004),
    (0x5000, 0x5004),
    (0x9000, 0x9004)
]

使用時の論理的な内容
ABCDEFGHIJKL
```

- 管理情報の各エントリには**開始アドレスと終了アドレス**を持たせれば、範囲の長さは差から求められる。**エントリの順番**が論理的な連結順を表す（追加の番号が必須とは決めていない）。
- **先頭アドレス**を入口として関連する断片情報を引く案。管理構造自体の形式、先頭断片の移動・解放時の扱いは未決定。
- **実際に利用する時だけ**、登録された複数のアドレスから読み、論理的に一つの可変長データとして扱いたい。
- 断片ごとに独立したアドレスを把握することで、**リンクの逐次追跡という依存関係を減らし、並行読込み・先読みを試す**方向。
- 「読み出し結果を物理的に新しい連続領域へコピーする」とは、現時点では決めていない。**コピーなしで地続きに扱えるか**を含め、実装方法を検証する。
- **CPUの仮想アドレスが実際に連続していること**と、**言語／ランタイムから論理的に連続データとして扱えること**は異なる。ページテーブルによる再マッピングを採用するとは決まっていない。

### 連続断片の管理情報の統合

例：`B+` の物理範囲が `0x3000〜0x3100`、次の論理断片 `B++` が `0x3100〜0x3200` なら、以下のように統合できる。

```text
統合前: B+  (0x3000, 0x3100)
        B++ (0x3100, 0x3200)

統合後: B+  (0x3000, 0x3200)
```

データ本体を移動せず、範囲情報を更新して余分なエントリを消す。ただし、物理アドレスが隣接していても**論理順が隣接していなければ**単純統合はできない。

## 4. 空き領域管理【方向性】

メモリをできるだけ**管理領域の先頭側から詰めて使用する**。この方針のもと、空き情報を次の2つに分ける。

1. **High Water Mark（HWM）:** 管理対象の連続したアドレス領域における、これまで使用した部分の終端。以降は、予約済みの管理領域内なら未使用と扱える。
2. **解放済みの穴（Free Ranges）:** HWMより前で解放された範囲について、**開始アドレスとサイズ**を記録する。

```text
管理領域の先頭                                    HWM
    |                                              |
    [使用中][空き32B][使用中][空き64B][使用中] | 未使用...

Free Ranges:
    (start: 0x1200, size: 32B)
    (start: 0x3500, size: 64B)
```

- 解放時には、**その時点で解放したアドレスと範囲を把握している**。メモリ全体の再走査を避け、対応する空き情報を更新する。
- 新規確保・可変長の伸長では、可能なら**先頭に近い解放済みの空き領域**から再利用。足りない分は別の空きやHWM以降を検討。
- 空き領域の一部を確保したら、**残余の開始アドレスとサイズを更新**する。
- **隣接する空き範囲は結合**する。末尾の使用領域が解放され、末尾側の空きが連続するなら**HWMを戻す**ことも可能。
- このHWMモデルが成立するのは、アロケータが管理する連続したアリーナなどに限る。**OS全体の物理RAMが常にHWM以降すべて空いているという意味ではない。**
- アラインメント、確保単位、最小割当サイズ、空きが小さすぎる場合、並行確保／解放は別途検討。
- 空き領域の**高速探索**をどう実現するかは未決定。単純なリストの先頭から探せば最悪時に穴の個数に比例する。

## 5. 寿命を意識した配置【最適化の仮説】

**長寿命データを前方、短寿命データを後方**に配置できれば、後方の解放時にHWMを戻しやすくなり、内部の穴を減らせる可能性がある。

ただし2026-10-30の面談で、**「後からもっと長生きさせたいオブジェクトもある」**との指摘があった。

- 生存期間は生成時に確定しないことがある。
- スタックは通常LIFO制約があり、任意の寿命延長・解放順序にそのまま対応できない。
- 寿命順配置は**必須の正しさの条件ではなく、可能な場合の最適化**とする。
- 寿命が確定しているもの、変更可能なもの、未確定なものをどう区別し、移動なしで寿命延長に対応するかは未設計。
- 言語仕様、Echoの検証、ユーザーに見せる解放操作との整合が必要。

## 6. ユーザーからの解放操作（free等）【未決定】

面談では「ユーザーに `free` などの操作をどう見せるのか」という論点が出た。

現段階で決めて**いない**こと：

- 明示的な `free()` の構文、引数、呼び出し責任。
- 固定長／可変長の解放操作の見せ方。
- 分割された可変長データを一度の操作で全断片解放する際の内部手順と、断片共有がある場合の扱い。
- 解放に必要なサイズ・範囲情報をどう確実に得るか。
- 解放後参照、二重解放、古いアドレスの再利用、並列参照中の解放をどう防ぐか。

**No GC / No Ownership**という研究方針だけでは、安全性の保証にはならない。Echoを含む静的・動的検証の分担は今後の研究課題。

「誰が・いつ解放したか」という**診断用の履歴**は、再利用に必要な**現在の空き範囲（アドレス・サイズ）**とは別物。履歴を全量保存するかも未決定。

## 7. 性能と実現性の注意【未実証】

この構想の狙いは**不要なデータ再配置と管理情報を減らし、分割可変長の参照性能を改善すること**であり、実証された優位性を主張するものではない。

- **各断片のアドレスを直接参照できる（個別操作のO(1)）**ことは、**1万断片を全部読む総時間がO(1)**という意味ではない。CPU同時実行数やメモリ帯域は有限。
- 断片の**論理的な連結読込み**と、CPUからの**通常の単一ポインタによる連続アクセス**は別。どのAPI/実装でどの意味の連続性を実現するか未確定。
- 断片が不均一長なら、任意の論理オフセットに対応する断片の探索も別問題であり、現状で**ランダムアクセス最悪O(1)は証明されていない**。
- 各断片の範囲を保存するので、メタデータは少なくとも断片数に応じて増える。実サイズ、追加の索引コスト、断片化を含めて評価する。
- 分割のたびに管理構造をどのように増やすか、並列読込みと更新を安全に両立できるかは未解決。
- 全体の空き容量を使い切れるとは限らない。アラインメントや最小確保量などの制約がある。

### 比較実験案

1. 断片数 **1 / 10 / 100 / 1,000 / 10,000** で、順次リンク辿り・アドレス範囲一覧・通常の連続バッファを比較。
2. **先頭だけ／中間だけ／末尾だけ／全体**の読込みを別々に測定。
3. データ量を一定にして断片数を変える実験と、断片サイズを一定にして総データ量を増やす実験を分ける。
4. 追加コピー量、実際の処理時間、メモリ帯域、キャッシュミス、メタデータ総量を測定。
5. 伸長・縮小・解放の繰り返しで、HWM、Free Ranges、断片の統合数、アロケーション失敗率、穴の残存量を確認。
6. 境界条件（空き0、空きの大量分割、重複解放、使用中解放、先頭断片解放、長期稼働）を検証する。

## 8. 新旧設計の区別

| 項目 | 2026-10-26の検討 | 2026-10-31時点の新方向 |
| --- | --- | --- |
| データ識別 | 全データ固有IDが基本 | 全データへの追加固有IDを前提にしない。直接アドレス参照を基本候補に |
| 可変長 | 親子ID（`16e#0`等） | 必要な場合だけ物理分割し、外部のアドレス範囲情報で論理統合 |
| 配置 | 16区間・リングを検討 | 先頭側から詰め、解放済みの穴を再利用する方向 |
| 空き | `ID:empty`の検討 | `(開始アドレス, サイズ)` とHWM |
| 参照 | ID → 中央表 → 区間内探索 | 先頭アドレスを入口として可変長断片範囲を解決する案 |
| 寿命 | 決定方式なし | 長寿命を前方に置く最適化案。ただし寿命延長等は未解決 |

**過去案は設計の履歴として残す。** 新方式もまだ正式採用・実装・ベンチマークが済んでいない。後の実験で前提を再検討する。

## 9. 次に設計・検証する課題

1. **使用時の読み込み方式:** 「各アドレスから同時に参照して、地続きに読む」をどの層で実現するか。全体読込みと部分読込みの区別。
2. **範囲一覧のデータ構造:** 順序保持、途中挿入・統合・削除、先頭アドレスからの到達、範囲の長さの扱い。
3. **Free Rangesの索引:** 先頭優先であっても探索に時間がかからない方式。
4. **寿命／解放API:** ユーザー操作、Echoの安全性確認、寿命延長、同時アクセス時の扱い。
5. **実測:** 既存のアロケータ・分割バッファ・Scatter/Gather等との公正な比較。

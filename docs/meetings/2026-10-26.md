## 1. 研究目標【基本方針】

目標は、**メモリの確保・解放・可変長データの伸縮に伴うコストを総合的に最小化する**こと。

- データのコピーと再配置を最小限にする。
- 空きメモリを柔軟に再利用し、断片化や無駄な予約領域を抑える。
- データの配置を自由にしても、参照・探索を高速に保つ。
- IDや管理表のメモリ使用量、生成・更新時間も小さく保つ。
- 配置最適化そのものが大量のデータ移動を誘発しないようにする。
- メモリの寿命管理・解放後参照・並行アクセスについて安全性を確立する。ただし、**具体的な安全性の実現方式は未決定**。

### 着想源について

- **コンシステントハッシュ法:** 構成変化があっても既存データの再配置の影響を小さくするという**設計原理**が出発点。**コンシステントハッシュ法をメモリ管理にそのまま移植することは決定していない。**
- **ファイルシステム:** 論理的な名前・データと実際の保存位置の分離。
- **仮想メモリ:** 物理的な位置と論理的なアドレスの対応付け。
- **階層探索、増分更新、既存メモリアロケータ:** 探索範囲の絞り込み、変化した部分だけの更新、空き領域の再利用。

「固定の既存方式を一つ採用する」のではなく、**配置方法とそれに適した高速参照アルゴリズムを一体で設計し、必要なら新しいアルゴリズムを作る**。

## 2. データ自身が固有IDを持つ【基本方針】

- **データ一つにつき固有IDを一つ持つ。**
- 固有IDは、位置を示すアドレスではなく、データを一意に区別するための**軽量なラベル**。
- データの実際の格納位置が変わっても、固有IDは維持する。
- データの配置は多少不規則でもよく、IDで発見できるようにする。
- 人間に見せる例として **16e、2af** などの16進数風の表記を使う。**0x接頭辞は付けない**。
- 固定64bit整数に限定しない。文字列のように長さ可変で扱える識別子、規則性を利用した圧縮符号化などを検討する。
- **16進数から32進数に表示基数を増やす**案も話題に出たが、基数の変更は主に*表示桁数*の問題であり、同じ識別可能数を表すための情報量自体は減らない。
- 生成規則が一意性を確実に保証できることが必要。単純なハッシュ値だけでは衝突の扱いが残る。

### 可変長データの親子ID【基本方針】

可変長データの追加部分には、親IDに子番号を付けたラベルを使う。

~~~text
16e
├── 16e#0
├── 16e#1
└── 16e#2
~~~

- 親がデータ全体、子がそのデータの追加部分などを識別する。
- **子番号は親ごとに #0 から順に発行する。**
- **子要素が一つでも残る限り、解放済み番号へ戻らず、次の番号を増加させる。**
- 子がすべて消えた後に子番号をどう扱うか（再開・リセットなど）は、安全性を踏まえて詳細未決定。
- ID文字列を毎回重複保存しなくても、親IDと子番号の規則性から表現できる可能性がある。
- 実際の子の配置は連続していても、離れていてもよい構想。子の数・サイズ・順序・論理オフセットの管理は未決定。

**注意:** IDの重複を防ぐことと、解放済みデータへの古い参照が新しいデータを指さないことは別問題。安全な再利用規則が必要。

## 3. 4bitの区間IDと階層的な探索【現在の具体案】

メモリ空間を**前半／後半へ再帰的に二分**し、4段階で**16区間（0〜f）**にする案。

~~~text
全体
├── 0 : 0〜7
│   ├── 00 : 0〜3
│   └── 01 : 4〜7
└── 1 : 8〜f
    ├── 10 : 8〜b
    └── 11 : c〜f
        ├── 110 : c〜d
        └── 111 : e〜f
~~~

例えば区間 **d** は16進数で **1101（二進数）**。分岐の経路 **1 → 11 → 110 → 1101** で目的の区間まで辿れる。

**区間IDは正確なバイトアドレスではない。** 目的のデータを探す**範囲を絞り込む情報**である。

区間接頭辞・データ固有ID・子IDを一体化した表示例：

~~~text
a_16e#2
│ │   └─ 子番号
│ └───── 固有ID
└─────── 区間ID（4bit）
~~~

- 区間IDは表示上、16進数1桁。
- 移動先が同じ区間なら、区間接頭辞は変わらない。
- 別区間へ移ると区間接頭辞だけが変わる。**固有ID 16e#2 の同一性は保つ**。
- 16区間の経路を辿る部分は最大4分岐。ただし、**区間内の検索まで4回で完了するわけではない**。

### 区間内探索【例は確認済み、性能は未検証】

例：**d_16e#0** を探す。

~~~text
区間 d
    d_2ab#0
    d_5ae
    d_16e#0
~~~

子番号 **#0** の有無で候補を絞り、その後 **16e** かどうかを照合する例が挙がった。

~~~text
#0 の候補
    d_2ab#0
    d_16e#0

固有ID 16e と照合
    d_16e#0  ← 対象
~~~

**注意:** これは識別情報による絞り込みの考え方。単純に全件走査して#0を照合するだけでは、大量のデータが存在すると高速性は保証できない。**区間内の配置順・索引・探索アルゴリズムを設計する必要がある。** そのため、区間分割だけで全探索が二分探索の計算量になるわけではない。

## 4. ID:empty による空き管理【基本方針】

- **空き場所／空き領域は ID:empty として表す。**
- 確保時には **empty → 固有ID** に変化する。
- 解放時には **固有ID → empty** に変化する。
- 管理機構自身が確保・解放・移動を行うため、**どのemptyが埋まり、どの場所がemptyになったかを、その操作の時点で把握している**。

例：

~~~text
移動前
    区間 a : a_16e#1
    区間 3 : 3_empty

移動後
    区間 a : a_empty
    区間 3 : 3_16e#1
~~~

**移動先のemptyを埋めた事実から配置先は分かるため、移動後にメモリ全体を探し直さなくてよい。**

- 空き領域の分割・統合、十分な容量の確認も検討対象。
- 区間全体が空なら、下位の区間管理を省略・集約できる可能性がある。
- **emptyの表現だけで、空き領域のサイズ・連続性まで自動的に分かるわけではない。** 粒度と容量情報は未確定。

## 5. 中央管理表による参照【基本方針】

**参照時の現在の区間情報は中央管理表で一元管理する。**

~~~text
プログラムが参照する不変のID
        16e#1
           ↓
      中央管理表
        16e#1 → a
           ↓
      区間 a を探す
           ↓
      16e#1 を発見
~~~

上の移動例なら、

~~~text
移動前: 16e#1 → a
移動後: 16e#1 → 3
~~~

- 更新するのは中央管理表の**最新の区間情報**。参照元のそれぞれが古い区間接頭辞を独立保持する方式にはしない。
- 区間情報は**4bit**なので値自体の更新は軽い。1バイトに2件を詰めることも情報量の上では可能。
- 実データの場所まで探す必要があるため、**中央表の検索コストと区間内の検索コストは別**に検証する。
- 頻繁に参照する場合、移動・解放が起きないと検証された区間で解決済みアドレスを一時的に使う最適化も検討できる。
- ただし古いアドレスが無効になった場合の保護や、並行処理との同期は**未解決**。

ここまでの基本設計では、**区間に基づく探索と、移動時の中央管理表の一箇所更新を連携する**。

## 6. 円形状のメモリ配置【新たな検討案】

16区間 **0〜f** を論理的に**円形（リング状）**に置いて考える。

- 区間 **f の次は 0** に回る。
- 内側から前半・後半、00／01／10／11、さらに最終16区間という**階層を重ねた円形表現**を考えた。
- 各区間にはデータやemptyがある。一つの区間に一つのデータしか入らないという制限は**置いていない**。
- 円形の順序を使って、配置先と空き領域をどう決めるかを考える。
- **円形の論理配置と、物理アドレスが円状であること・実際に連続していることは別**。具体的なメモリ上の対応は未定義。

### コンシステントハッシュ法に着想を得た擬似実験【正式採用ではない】

試した仮ルール：

1. IDから配置の起点を決める。例として親 **16e** の起点を区間 **5** と仮置き。
2. 新しい子要素を配置するとき、リング上を時計回りに探索してemptyを探す。
3. emptyを見つけたら新しい子を配置し、既存データは原則移動させない。
4. 中央管理表に固有IDと現在の区間を反映する。

これは**擬似的なリング配置の検討**であり、実際のコンシステントハッシュ法の性能保証やデータ再配置特性がそのまま成立するとは未確認。

検討した配置戦略：

| 戦略案 | 目的・注意点 |
| --- | --- |
| 親子の近接配置 | 可変長データの子を近くに置き、参照や連続アクセスを改善できるか |
| アクセス傾向による配置 | よく一緒に使うデータをまとめ、CPUキャッシュの局所性を改善できるか |
| 空き容量に応じた配置 | サイズの合うemptyを再利用し、断片化を抑えられるか |
| 伸長しやすさの考慮 | 将来の追加データを置く余地を残すか。予約し過ぎの浪費に注意 |
| 再配置の局所化 | 必要になっても既存データの移動をできるだけ小範囲に抑える |

これらは**比較対象の候補**であり、採用規則は未決定。

## 7. 配置からemptyまで把握する【今回の重要な方向性】

この議論で特に重視したのは、**「データの配置規則を見れば、どこが空いているかも効率よく分かる」方式**。

- データと空き領域の管理を別々に大きく持つのではなく、**配置方法と空き領域の探索を連動**させる。
- emptyを見つけるために、メモリ全体を毎回走査しない。
- データの確保・解放で変わった場所は管理機構がすでに知っているので、変更された情報だけを更新できる。
- 区間ごとのemptyの有無だけなら、16区間で**16bit（2B）のビット集合**にまとめる案もある。ただし、どのサイズのデータを収められるかはこれだけでは判断できない。
- 区間の空き情報を階層的にまとめれば、満杯の枝をスキップできる可能性がある。
- データを後から大量に動かして空きを整えるより、**新規配置の段階で将来の伸縮と参照効率も考慮する**案が出た。

**狙い:** 低再配置コスト・高速参照・空き領域の高速発見が、同じ配置規則から得られること。

## 8. 軽量化と評価指標【目標、未達成】

**追加管理情報は、共有管理情報も含めて平均8B以下／データを目指す**という研究目標を置いた。

注意事項：

- ID自体の16進数表記が短くても、索引・表・状態・データサイズ・解放管理のコストは残る。
- 区間IDが4bitだからといって、管理表全体が4bit／データになるわけではない。
- 子IDは親IDと連番から導出して重複情報を省ける可能性がある。
- 固定長64bitに限らず、可変長ラベルやコンパクトな符号化を検討する。
- データが非常に小さい場合、IDと管理表の費用が本体より大きくなる可能性がある。
- 16区間に絞っても、区間内探索や中央管理表の索引に時間がかかれば総合的に不利になる。

**評価したい指標：**

1. 1データあたりの実際の管理バイト数（共有表・木・断片化を含む）。
2. 固有IDの発行・子IDの生成・解放コスト。
3. 中央管理表と区間内検索の処理時間・比較回数。
4. 可変長伸縮・確保・解放による既存データのコピー量。
5. 外部断片化・内部断片化・空きの有効利用率。
6. 連続アクセス・ランダムアクセス・親子データ参照の速度とキャッシュ効率。
7. 長期間の生成／解放でIDが枯渇・衝突・誤再利用しないか。
8. 同時アクセス、移動、解放で安全性を維持できるか。

**既存アロケータは解放のたびに必ず前詰めするわけではない。** 比較は実在の高性能アロケータや複数の可変長データ構造に対して行う。

## 9. MIR・Analyzerとの連携【検討中】

既に設計しているコンパイラは、

~~~text
Source → MIR Generator → MIR → Analyzer → (MIR + Analysis) → Backend → Machine Code
~~~

- コンパイル時に、データの論理的な識別・参照関係・解放可能性・影響範囲を解析し、**MIRとは独立したAnalysis**へ記録することを検討。
- 実行時には、中央管理表が生成済みデータの現在の区間・状態を管理する。
- **コンパイル時の識別子と実行時の固有IDは区別が必要。** 同じ生成命令がループで何度も実行されれば、別の実行時データが生成される。
- Analyzerが安全に証明できた処理区間で、参照の再解決を省く最適化は候補。ただし移動・解放・並行性に関する保証の方式は未決定。

## 11. 今回の合意・次の研究ステップ

### 合意した基本的な考え方

- **配置方法とそれに適した参照アルゴリズムを一緒に作る。**
- **データの固有IDは同一性、区間接頭辞は探索範囲、子番号は可変長の一部分**を表す。
- **empty**を活用し、どこが埋まり、どこが空いたかを管理機構が把握する。
- 現在の区間情報は**中央管理表**に集約し、移動時には更新対象を局所化する。
- 円形の16区間で、配置規則から**データの発見だけでなく空きの把握も高速化**できないか考える。
- **コンシステントハッシュ法に限定せず**、既存技術と新しい配置・探索アルゴリズムを検討する。

### 次の検証案

- 16区間リングの各区間に**複数の可変サイズデータとempty**を置く。
- **確保・解放・伸長・縮小**を繰り返して、中央管理表と空き状態の更新を追跡する。
- 近接優先・容量優先・空き管理優先などの配置案を同条件で比較する。
- 区間内探索、実データ移動量、管理情報の総バイト数、アクセス速度を測る。
- 特に、**空きが偏り、断片化した場合**の振る舞いを検証する。

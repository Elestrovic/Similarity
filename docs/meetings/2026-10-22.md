## 1. セルフホスティング優先への転換

### 1.1 目標

**Similarityを完成させてからセルフホスティングするのではなく、Similarity自身でSimilarity製コンパイラを書ける最小の言語機能を固め、早期にセルフホスティングする。**

概念的な検証段階：

1. **Stage 0:** 既存の実装（ブートストラップ用コンパイラ）がSimilarity製コンパイラのソースをコンパイル。
2. **Stage 1:** 得られたSimilarity製コンパイラが自分自身のソースをコンパイル。
3. **Stage 2:** 得られたコンパイラの出力と動作を検証し、自力で再ビルドできることを確認。

最初は対応OSやアーキテクチャを限定してよい。言語機能の最終形、独自メモリ管理方式の最終形、標準ライブラリ全体を完成させることは、最初のセルフホスティングの**必須条件ではない**。

### 1.2 必要な能力（各項目を専用の文法にする必要はない）

| 領域 | 必要な能力・用途 |
| --- | --- |
| 基本値 | 整数、真偽値、文字／バイト列など |
| 変数 | 宣言、参照、更新 |
| 式 | 算術・比較・ビット演算、明確な型規則 |
| 関数 | 定義、引数、呼び出し、戻り値 |
| 制御フロー | 条件分岐、反復／探索、終了 |
| データ構造 | Token、状態、シンボルなど複数の値の管理 |
| メモリ | 確保、読み書き、参照、安全な解放 |
| 入出力 | ソース読み込み、生成物の書き出し |
| エラー | 構文・型・実行環境の異常の扱い |

**保留:** コンパイラ内部がTokenizer→Parser→ASTを採るか、Source→Analyzer等の別経路を採るかは、この会議では確定していない。まず言語が備えるべき能力から逆算する。

## 2. No Guessing と型システム

### 2.1 合意した基本原則

- **値を扱う箇所や宣言が型情報を与える。**
- 型が宣言済みであれば、それを参照してよい。毎回型を再記述する必要はない。
- 明示された情報および**定義済みの言語規則**から一意に決まる場合は型推論を認める。
- 複数候補が残るのに、コンパイラが勝手に選ぶことはしない。
- 初期の「すべての数値に毎回明示的な型が必要」という考え方は**緩和**された。

例：

```similarity
print_i32(+(10,20))
print(i32(+(10,20)))
```

両方とも30を出力する意図であり、`i32` の適用範囲は異なる。

### 2.2 printの2方式 — **単なる別表記ではない**

| 書式 | 型の適用範囲 | 解釈 |
| --- | --- | --- |
| `print_i32(+(10,20))` | `print` の呼び出し全体 | この`print`呼び出しは`i32`値しか受け付けない。内部の演算にもその型制約が及ぶ |
| `print(i32(+(10,20)))` | `i32(...)` の内部 | `i32` が指定された内部の値／式に適用される。`print` 自体を `i32` 専用にはしない |

`print_i32` を型別の「別関数」として増殖させる意図ではない。`print` という処理への型情報の付加である。

`print(3)` のように型情報が直接書かれていない呼び出しについても、**一意に決まる言語規則があれば許可する**方向。整数リテラルの標準型や曖昧性解消の規則は未確定。

### 2.3 宣言で既知なら推論できる

以下はフィールド宣言から型が分かる構文候補の例：

```similarity
Struct[
    let{
        Todo(
            id(type:i32),
            title(type:string),
            done(type:bool)
        )
    }
]

Todo[
    let{
        task(
            id:3,
            title:"Similarity",
            done:false
        )
    }
]
```

`id:3` で `i32(3)` と繰り返さなくても、`id` の宣言型が `i32` と分かる。ここでのStruct構文は**仮案**である。

数値の例として、`42` を `i32`、`3.14` を `f32` とする**デフォルト型規則を定義する可能性**が挙がったが、**型・整数幅・精度・範囲外の挙動まで確定したわけではない**。

### 2.4 関数の引数と戻り値は独立

引数は関数への**入力**、戻り値は関数からの**出力**。引数が `i32` だからといって戻り値を `i32` に限定しない。

```similarity
Func[
    let{check},
    func_argument{
        func_check:func_n(type:i32)
    },
    check{
        If[
            conditions{>(func_n,i32(0))},
            truth{return(bool(true))},
            failure{return(bool(false))}
        ]
    }
]
```

戻り値型は以下から分かるなら再記述不要：

- `return(result)`：`result` の変数宣言の型。
- `return(func_n)`：`func_n` の引数宣言の型。
- `return(+(func_n,func_n))`：引数型と演算規則から定まる型。
- `return(i64(100))`：明示された型。
- `return(42)`：数値リテラルの型決定規則が定義され、一意に決まる場合のみ推論可。

複数の `return` が異なる型（`i32` と `i64` など）になる場合、**勝手な型選択は行わず、型情報・整合性を明確にすることを求める**。その具体的な宣言構文、許す変換、エラールールは保留。

## 3. 複数引数の識別

### 3.1 初期の検討

候補として以下が登場した：

- `func_add_1`、`func_add_2`：**採用しない方向**。識別子自体に番号を埋め込みたくない。
- `func_add<1>`：新たな表記がしっくりこなかった。
- `func_add.1`、`func_add.2`：**位置を区別する記法として有力**。
- `id:1`、`id:2` を宣言する案もあったが、宣言量の増加が課題だった。

### 3.2 同名・同型の引数をまとめる案

```similarity
Func[
    let{add},
    func_argument{
        func_add(type:i32)
    },
    add{
        return(+(func_add.1,func_add.2))
    }
]
```

- `func_add` という基本名と `i32` を宣言。
- `func_add.1`、`func_add.2` のような**実際の参照**により位置を区別。
- この初期案では、使用する最大番号によりコンパイル時に必要個数を導くことを検討した。
- **途中の番号が欠けたらエラー**。例えば `.1` と `.3` があり `.2` がない場合はコンパイルエラー。

ただし、番号なしの `func_add` の正確な意味、未参照の引数の扱い、呼び出し側と引数個数の整合性、型や順序をいつ固定するかは引き続き検討が必要。

### 3.3 異なる型の引数

```similarity
func_argument{
    func_add.1(type:i32),
    func_add.2(type:string)
}
```

型は宣言側にあるので、使用時は `func_add.1`、`func_add.2` で十分。`func_add.i32.1` のように型を繰り返す必要はない。

## 4. until：汎用的な閉区間（Inclusive Range）

### 4.1 基本形

```similarity
until(start:i32(1),end:i32(5))
```

範囲は **1, 2, 3, 4, 5**。`end` を**含む**ことは合意済み。

- `until` は「○から○まで」を表す汎用的な範囲表現として検討。
- 単体でループを実行するとは限らない。受け手が範囲をどう利用するかを決める方向。
- 引数宣言だけでなく、探索・配列・メモリ範囲などへの一般化が候補。

ステップ幅、逆方向、データ型、異常範囲、範囲の実体化、空範囲、メモリ上の表現、他機能での使い方は未確定。

### 4.2 同型引数の範囲指定

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        end:func_add.3
    ),
    func_add.4(type:string)
}
```

これは**引数宣言という文脈では**次の展開を意図する：

```similarity
func_argument{
    func_add.1(type:i32),
    func_add.2(type:i32),
    func_add.3(type:i32),
    func_add.4(type:string)
}
```

開始地点の `type:i32` を範囲内に利用する。`end` 側に同じ型を書き直す必要はない。

## 5. until 内の here と asfor

**基本モデル:** `start` が基本情報を指定し、`here` は特定地点からの継続的変更、`asfor` は一要素だけの例外を表す。少なくとも引数宣言における型指定の意味は次のとおり。

### 5.1 asfor — **その要素だけ**

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        asfor:func_add.3(type:string),
        end:func_add.4
    )
}
```

展開：

| 引数位置 | 型 |
| --- | --- |
| `func_add.1` | `i32` |
| `func_add.2` | `i32` |
| `func_add.3` | `string`（`asfor` の対象のみ） |
| `func_add.4` | `i32`（元の基本型に戻る） |

`asfor` は**以降の型を切り替えない**。

### 5.2 here — **そこから先**

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        here:func_add.3(type:string),
        end:func_add.4
    )
}
```

展開：`.1`～`.2` は `i32`、`.3`～`.4` は `string`。

### 5.3 複数の here

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        here:func_add.5(type:string),
        here:func_add.8(type:i64),
        end:func_add.10
    )
}
```

| 範囲（両端含む） | 型 |
| --- | --- |
| `.1` ～ `.4` | `i32` |
| `.5` ～ `.7` | `string` |
| `.8` ～ `.10` | `i64` |

`here` が次に現れた時点で、その位置から新しい指定内容に切り替わる。

### 5.4 here と asfor の組み合わせ

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        here:func_add.5(type:string),
        asfor:func_add.6(type:bool),
        here:func_add.8(type:i64),
        end:func_add.10
    )
}
```

展開の型は：

| 位置 | 型 | 理由 |
| --- | --- | --- |
| `.1`～`.4` | `i32` | `start` |
| `.5` | `string` | 1回目の`here` |
| `.6` | `bool` | この位置だけ`asfor` |
| `.7` | `string` | `here` の指定に戻る |
| `.8`～`.10` | `i64` | 2回目の`here` |

**この組み合わせで、連続する区間と単発の例外を両方表現できる。**

### 5.5 here と asfor の同一地点での衝突

ユーザーが明示した衝突対象は**「here と asfor の指定地点が同じ」**ケース。`here` が前から有効なだけで、別地点の `asfor` を機械的にエラー扱いする、という話ではない。

**同じ地点・同じ型 → 冗長な二重指定エラー**

```similarity
until(
    start:func_add.1(type:i32),
    here:func_add.3(type:string),
    asfor:func_add.3(type:string),
    end:func_add.5
)
```

`func_add.3` への `string` 指定が重複。コンパイラは `asfor` が不要なので削除するようエラーで求める。

**同じ地点・異なる型 → 型衝突エラー**

```similarity
until(
    start:func_add.1(type:i32),
    here:func_add.3(type:string),
    asfor:func_add.3(type:i64),
    end:func_add.5
)
```

同じ `func_add.3` に `string` と `i64` の異なる明示指定がある。コンパイラがどちらかを独断で選ぶことはせず、エラーとする。

| ケース | 判定 |
| --- | --- |
| `here` と `asfor` が同じ位置・同じ型 | 冗長エラー（重複した`asfor`を除去するよう要求） |
| `here` と `asfor` が同じ位置・違う型 | 衝突エラー |
| `here` と `asfor` の明示的な指定地点が異なる | この衝突規則の対象外 |

**未定義事項:** `start` と `here` が同じ位置、複数 `here` または複数 `asfor` が同一位置、範囲外の指定、順不同の指定、型以外への適用などは別途仕様化する。

## 6. コンパイラが検証すべき例（将来のテスト仕様候補）

| 入力・状況 | 期待する意味／結果 | ステータス |
| --- | --- | --- |
| `until(start:i32(1),end:i32(5))` | 1～5、5も含む | 合意 |
| `until(start:func_add.1(type:i32),end:func_add.3)` | .1～.3 は i32 | 合意した引数宣言案 |
| `here:func_add.3(type:string)` | .3から次のhere／終点までstring | 合意した案 |
| `asfor:func_add.3(type:string)` | .3だけstring | 合意した案 |
| `here` と `asfor` が同じ .3 で同型 | 冗長エラー | 合意 |
| `here` と `asfor` が同じ .3 で異型 | 型衝突エラー | 合意 |
| `func_add.1` と `func_add.3` のみ参照 | `.2` 欠番エラー | 合意 |
| `print_i32(+(10,20))` | i32制約の下で加算・出力 | 合意 |
| `print(i32(+(10,20)))` | i32の局所指定で加算・出力 | 合意 |
| 宣言型が既知の`return(variable)` | 既知の型を使用 | 合意した原則 |
| 複数のreturnが異型 | コンパイラが勝手に統一しない | 具体規則は未定 |

## 7. 未解決の論点

1. **範囲一般:** `until` の対象となる値・位置の型、ステップ、逆方向、範囲外・空範囲、順序、複数範囲の合成。
2. **範囲の指定内容:** `here`／`asfor` を型以外にどう利用するか。汎用機能としての正式な意味論。
3. **引数の宣言と個数:** 同型一括宣言の推定個数と、`until` による明示範囲指定をどう統合するか。未使用引数や呼び出し時の引数数の扱い。
4. **識別子:** `func_add.1` の解析規則、デフォルト引数名と改名 `func_fib:func_n(type:i32)` との統合、異なる関数・モジュール間の衝突。
5. **型推論:** 整数・小数リテラルのデフォルト型、範囲外数値、型変換、型付き演算の結果型。
6. **戻り値:** 異なる型のreturnが混在するときの明示構文やエラー規則、複数戻り値、returnなし。
7. **セルフホスティング:** データ構造、文字列／バイト列、メモリ操作、Explore、I/O、エラーの最小仕様とブートストラップ検証。
8. **実装可能性:** 現在のGitHub上の処理系・文法と、この新しい設計案の差分確認。

## 8. 次の検討順序（提案）

1. Tokenやシンボルを表現するための**構造体・集合・バイト列**の必要最小限の仕様を考える。
2. 上記の`func_argument`と`until`の例を、正式な字句・構文・意味規則へ落とす。
3. 小さなプログラムで型推論／関数呼び出し／戻り値の整合性を試す。
4. **セルフホスティングに必要な最低限の処理系**を先に実装し、Stage 0→Stage 1→Stage 2を検証する。

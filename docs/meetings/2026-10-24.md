## 1. 設計の目的【合意した方向性】

Similarityでは、コンパイル・最適化のためだけでなく、**何十年後でもプログラムの動作・処理の役割を再解析／再構築できるような中間表現**を目指す。

- MIRは**高水準寄りの中水準IR（Middle-level IR）**とする方向。
- ソース構文を丸ごと複製するのではなく、実行に必要な操作・型・構造などを保持する。
- 命令を低水準化しすぎて処理の意味や関係を失わないようにする。
- 将来のAnalyzerが新しい方式で再検証できるよう、**MIRの本体は解析結果から独立して再解析可能**であるべき。
- 「50年後も必ず安全」という主張ではない。意味論の保存、再検証、外部依存・安全性規則の扱いを今後定義する必要がある。

### Explanationと処理の目的

ソースコードの先頭のExplanationが、プログラムの大まかな目的を伝える案：

§§§similarity
Explanation[
    Algorithm{Fibonacci}
]
§§§

- Explanationは、「フィボナッチ数列を扱う」という**意図の手がかり**としてMIRに保持する。
- 各ループや各演算のPurposeをプログラマーが毎回手書きする方式にはしない方向。
- 将来のAnalyzerは、MIRの制御フロー・データフロー・演算・初期値などを照合して、個々の処理の**役割を再構築できる可能性**を目指す。
- **ExplanationがFibonacciと書いてあるだけでは、どのループが何を実現しているかは証明できない。** 意図の記述と実際の動作・安全性の証明は分けて扱う。
- MIRにあらかじめ§purpose: FibonacciLoop§などの推定結果を確定的に埋め込む必要はない。将来、根拠を用いて再解析できればよい。

## 2. コンパイラ全体の流れ【合意した構成】

§§§text
Source Code (+ Explanation)
          ↓
     MIR Generator
          ↓
         MIR
          ↓
       Analyzer
          ↓
      MIR + Analysis
          ↓
        Backend
          ↓
      Machine Code
§§§

- **MIR Generator:** ソースを読み、処理の構造と、ソースから**すでに確定している情報**をMIRに記録する。
- **MIR:** 実行の意味・構造・明示的な型や値・Explanationなどを保持する。
- **Analyzer:** MIRを入力として、型の推論、明示情報の整合性検証、依存関係・安全性などを解析する。
- **Analysis:** Analyzerが導出した情報を、**MIR本体とは独立した情報**として保持する。
- **Backend:** MIRと、対応するAnalysisの情報を参照して機械語を生成する。

### MIRは書き換えず、解析情報を足す【合意】

Analyzerの基本動作は、**MIRの処理構造を書き換えることではなく、MIRに必要な解析情報を追加すること**。

さらにその追加情報は、MIRに直接混ぜず、**MIRに紐づく独立したAnalysis**として扱う方針。BackendにはMIRとAnalysisの組を渡す。

Analyzerが証明できない性質を断定しない。必要な検査に失敗した場合、Backendに安全なものとして扱わせないための検証ルールが必要だが、検証状態の表現方法は未確定。

## 3. MIR Generatorが拾う情報【合意】

MIR Generatorは単なるテキストの置換器ではない。**ソースに書かれていて意味が明確な型や初期値は、その段階ですでに拾う。**

例：

§§§similarity
let{x(type:i32,value:18)}
§§§

説明用MIR：

§§§text
Variable #1
    name: x
    declared_type: i32
    initial_value: 18
§§§

- §i32§ と §18§ はすでにソースに明記されている。
- その事実をMIRに記録するためにAnalyzerで「推論」し直す必要はない。
- ただし、その型・初期値が妥当か、値の型や範囲が矛盾していないかは**Analyzerが検証する**。

もう少し複雑な例：

§§§similarity
let{x(type:i32,value:18)}
let{y(type:i32,value:24)}
let{z(value:+(x,y))}
§§§

説明用MIR：

§§§text
Variables
    #1 x : i32 = 18
    #2 y : i32 = 24
    #3 z = add(x,y)
§§§

説明用の独立Analysis：

§§§text
Analysis
    #3
        inferred_type: i32
        depends_on: [#1,#2]
§§§

- §x§、§y§ は宣言型をMIRに保持する。
- §z§ の型は明示されていない。**型が一意に決まる演算規則を採用した場合**、Analyzerが§i32§と推論してAnalysisに記録できる。
- 推論不能・曖昧な場合は勝手に型を選ばない（No Guessing）。
- MIR本体の§#3 z = add(x,y)§を推論結果で上書きする必要はない。

## 4. MIR本体の内部構造【合意した方向性】

**階層構造を基本とする**。

例（概念図）：

§§§text
MIR
└── Module
    ├── Explanation: Fibonacci
    └── Function: main
        ├── Variable: a
        │   ├── Type: i32
        │   └── Initial: 0
        ├── Variable: b
        │   ├── Type: i32
        │   └── Initial: 1
        └── Loop
            ├── Output
            ├── Calculation
            └── Update
§§§

- 関数・分岐・ループと、その内部の処理の**所属関係**を保持できる。
- 制御フローとデータフローを将来再構築できるだけの情報も必要。ただし、具体的にどう保持するかは**未確定**。
- ソースの構文上の階層とMIRの意味上の階層を常に一対一にするとはまだ決めていない。

### 要素IDとAnalysisの紐づけ【有力な提案／詳細未確定】

§§§text
MIR
    Function #10
        Variable #11
        Variable #12
        Loop #13
            Operation #14
            Operation #15

Analysis
    #14
        type: i32
        depends_on: [#11,#12]
§§§

- 各要素に識別IDを持たせ、Analysisから参照する案。
- 差分再コンパイルを行うなら、編集により無関係な要素のIDが無意味に変化しないことが望ましい。
- **IDの生成方法・寿命・衝突回避・スコープ・永続化はまだ決定していない。**

## 5. MIRとAnalysisの分離による再コンパイル【合意した方針と期待】

**AnalysisをMIRから独立させる**ことは、差分再コンパイルに役立つ可能性がある。

想定する処理：

1. MIRの新旧状態を比較して、変更された要素を特定する。
2. 変更要素に依存するAnalysisを特定する。
3. 有効なキャッシュだけ再利用し、影響範囲のAnalysisを再計算する。
4. MIR本体と新たなAnalysisをBackendに渡す。

説明用例：

§§§text
MIR
    #1 = load a
    #2 = load b
    #3 = add #1,#2
    #4 = return #3

Analysis
    #3 depends_on [#1,#2]
    #4 depends_on [#3]
§§§

§#3§ が変更されれば§#3§と§#4§の解析結果が影響を受ける可能性がある。一方§#1§／§#2§に紐づく結果を再利用できる場合がある。

**重要:** 単に処理IDが変わらないから再利用可能、とは限らない。型定義、参照関係、外部インターフェース、MIRの意味論、Analyzerのバージョン、安全性規則などの変更もキャッシュ無効化条件になり得る。

### 長期保存・再解析

- **MIR本体:** プログラムの意味を再構築するために必要な情報を残す。
- **Analysis:** 計算・検証で導出された情報として扱い、必要なら破棄・再生成できる。
- 50年後にAnalysisを再生成するため、**動作を規定する基本型、制約、制御構造、操作の意味などをAnalysisにしか置かない設計は避ける**方向。
- 演算・型・安全性前提の意味を識別するために、MIRの形式・意味論の**バージョン付け**も有力。ただし形式は未決定。

## 6. MIRの情報要素【検討用の分類】

| 要素 | 保存する意図 | 状態 |
| --- | --- | --- |
| Header／意味論のバージョン | 将来の読み取り・互換性確認 | 提案、形式未確定 |
| Explanation | プログラム全体の意図 | MIRに保持する方向で合意 |
| Operation | 実行される処理内容 | 合意、命令セット未確定 |
| Type／Source Facts | 明示された型、値、制約 | MIR Generatorで取得する方針に合意 |
| Structure／Relation | 関数・ループの所属、処理関係 | 階層を基本とする方針に合意 |
| Node ID | MIRとAnalysisの関連付け | 有力案、方式未確定 |
| Analysis（別保存） | 推論・依存関係・検証結果 | MIRから分離する方針に合意 |

## 7. 決まっていないこと【今後の議論】

1. **MIRの最小単位と演算の粒度。** たとえば§+(a,*(b,c))§をどう構造化するか。
2. **正式なMIR構文／内部データ形式／保存方式。** テキストかバイナリか、どちらを正本とするか。
3. **制御フロー・データフローの明示表現。** 階層だけでは表現しづらいジャンプや参照をどう扱うか。
4. **識別ID。** 生成・安定性・変更検出・Analysisとの紐づけ。
5. **Analysisの具体的なスキーマと依存情報。** 型情報・検証結果・証明の保存方法。
6. **無効化と差分解析。** ソース変更だけでなくAnalyzerや意味論の変更をどう検出するか。
7. **Explanationと再構築。** 目的の照合方法、照合不能時の扱い、意味的な証明との区別。
8. **MIRの長期互換性。** 仕様バージョン、形式移行、外部依存、長期的な安全性検証。
9. **GeneratorとAnalyzerの厳密な境界。** ソースから確定する情報と、検証・名前解決などで確定する情報の分類。
10. **Backendとの受け渡し。** 機械語生成前に保証すべきAnalysisの検証条件。

## 8. 次の作業案

**§+(a,*(b,c))§ と、小さな関数・条件分岐・ループをMIRに実際に書き下し、階層構造と最小単位を比較検討する。**

最初からすべての命令と形式を決めるのではなく、少数の例から必要な情報を抽出する。

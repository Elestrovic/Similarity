# Similarity 言語設計 — 現在の合意事項と検討点

**更新:** 2026-10-24  
**ステータス:** 設計中の言語。**現行のGitHub版コンパイラが受理する構文の一覧ではありません。**

基本資料: [2026-10-19 議事録](meetings/2026-10-19.md) / [2026-10-22 議事録](meetings/2026-10-22.md)

## 1. 目的と原則【合意した方針】

Similarityは、低レイヤーのシステムプログラミングを**速く、安全に、シンプルに**行うことを同時に追求する研究的な言語です。

- GCを前提としない。Rust方式のownershipをそのまま採用する方針でもない。ただし、安全なメモリ管理の実際の解決方式は未決定。
- コンパイラは曖昧な内容を勝手に選ばない（**No Guessing**）。
- **定義済みの規則から一意に決定できる型推論は許す**。すでに分かっている型を毎回再記述しない。
- 使いやすさを犠牲にしてまで、従来方式の制約や複雑な構文をそのまま採用しない。
- 完成を待たず、セルフホスティングに必要な最小機能を優先する。

## 2. 文法上の共通要素【合意した方向性】

名前と括弧を組み合わせる：

```similarity
name[ ... ]
name{ ... }
name( ... )
```

`:` は対応関係など、`,` は要素の区切りに用いる。括弧は再帰的にネストできる。以前の`Category[Operation{Argument}]`は設計の出発点だが、**すべての式を厳密な三段構造に固定するわけではない**。

- 演算は**前置記法**（Polish notation）の方向。

```similarity
+(a,b)
*(3,+(x,2))
>=(n,10)
```

**未確定:** 括弧ごとの形式的な役割、演算規則、宣言スコープ、評価順序、識別子文法、数値と文字列の字句仕様、エラー文法。

## 3. 関数と型推論【合意した意味／構文は候補】

```similarity
Func[
    let{add},
    func_argument{
        func_add.1(type:i32),
        func_add.2(type:i32)
    },
    add{
        return(+(func_add.1,func_add.2))
    }
]
```

上記は**議論を表すサンプル**であり、コンパイル可能な実装確認済みプログラムではありません。

- `func_add.1`、`func_add.2` は、同一関数の引数を**番号で識別**する案。
- **欠番を許さない。** 例: `.1` と `.3` を扱うとき `.2` が欠けるならコンパイルエラー。
- 個々の引数に型が宣言されていれば、参照時に改めて型を付けない。
- 引数の型と関数の戻り値の型は別。`i32` を受け取る関数が必ず `i32` を返すわけではない。
- `return(variable)` はその変数の宣言型を、`return(expression)` は確定した式の型を利用してよい。
- 引数名を `func_fib:func_n(type:i32)` のように**変更元と変更先を明記**する案がある。別関数であっても変更先の名前が衝突する場合はエラーにする意図。

**未確定:** 識別子の衝突範囲、番号と実引数の対応、最大参照番号からの個数推論、引数を使わない場合、戻り値の型が複数に割れる場合、オーバーロード・型変換。

### 3.1 型情報の適用範囲【合意した意味】

```similarity
print_i32(+(10,20))
print(i32(+(10,20)))
```

- `print_i32(...)` は、独立した名前の関数`print_i32`を呼ぶ意味ではなく、**`print` の呼び出し全体**への `i32` 制約。内側の演算にも型制約が及ぶ。
- `print(i32(...))` は、内側の`i32(...)`部分にだけ型を指定する。外側の`print`は`i32`限定とはならない。

`42` や `3.14` のような数値リテラルに、言語で**決定的なデフォルト型**を定める方向を検討。`i32`／`f32` 等をデフォルトにするか、幅や精度は未確定。

## 4. until【合意した範囲の意味／実装方法は未確定】

`until` は単なる関数引数の糖衣構文ではなく、**汎用的な範囲表現**として検討している。`end` は**終点を含む**。

```similarity
until(start:i32(1),end:i32(5))
```

意図する範囲は **1, 2, 3, 4, 5**。

引数宣言の文脈では、

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        end:func_add.3
    )
}
```

は、`func_add.1`、`func_add.2`、`func_add.3`をいずれも`i32`として宣言する意図。

**未確定:** 単体で値を生成するか、どのような範囲を扱えるか、ステップ、降順、評価・展開タイミング、型以外への汎用的な適用方法。

### 4.1 here — **指定地点から次のhere／終点まで**

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        here:func_add.5(type:string),
        here:func_add.8(type:i64),
        end:func_add.10
    )
}
```

| 位置 | 型 |
| --- | --- |
| `.1`〜`.4` | `i32` |
| `.5`〜`.7` | `string` |
| `.8`〜`.10` | `i64` |

### 4.2 asfor — **その位置だけ**

```similarity
func_argument{
    until(
        start:func_add.1(type:i32),
        asfor:func_add.3(type:string),
        end:func_add.4
    )
}
```

`.1`／`.2`／`.4`は`i32`、**`.3`だけ`string`**。`asfor`の指定は後続まで持続しない。

`here`と組み合わせる場合：

```similarity
until(
    start:func_add.1(type:i32),
    here:func_add.5(type:string),
    asfor:func_add.6(type:bool),
    here:func_add.8(type:i64),
    end:func_add.10
)
```

`.5`は`string`、**`.6`だけ`bool`**、`.7`は`string`に戻り、`.8`〜`.10`は`i64`になる。

### 4.3 明示的な同一地点への二重指定【合意した検査】

**これは「前のhereの適用範囲に入るかどうか」とは別の条件。**

- `here` と `asfor` が**同じ位置**を指定し、**同じ型**を明記 → **冗長指定エラー**。`asfor`を消すよう求める。
- 同じ位置を指定し、**異なる型**を明記 → **型衝突エラー**。どちらかを勝手に選ばない。
- **指定位置が異なる**場合は、この同一地点の二重指定エラーの対象ではない。

```similarity
# 冗長指定エラー（.3にstringを二重指定）
until(
    start:func_add.1(type:i32),
    here:func_add.3(type:string),
    asfor:func_add.3(type:string),
    end:func_add.5
)

# 型衝突エラー（.3にstringとi64を指定）
until(
    start:func_add.1(type:i32),
    here:func_add.3(type:string),
    asfor:func_add.3(type:i64),
    end:func_add.5
)
```

**未確定:** `start`／`here`／`asfor`の同一地点衝突の残りの組み合わせ、同種の複数指定、範囲外番号、順不同、型以外の属性の競合。

## 5. その他の検討構文【未確定】

- `Var[let{...}]` の変数宣言。
- `If[conditions{...},truth{...},failure{...}]` の条件分岐。
- `Explore[search_area{...},how_explore{...},check{...}]` の探索・反復抽象化。終了判定の時点や各項目の正確な意味は未決定。
- `Struct` 等のデータ構造。セルフホスティングに必要だが、宣言と初期化の書き方は未決定。
- メモリを4領域へ分けて扱う発想等が議論されたが、具体的な安全性・アドレス表現・性能の検証は未了。これを実装済みの方式として扱わない。

## 1. 研究目的・設計思想

Similarityは低レイヤー向けシステムプログラミング言語を目指す。

- **安全性・速度・シンプルさを同時に高い水準へ近づける**。個々のトレードオフを無条件に受け入れず検証する。
- 必要のない文法規則や暗黙の動作を増やさず、コードから意図を読み取れるようにする。
- 既存言語の `for`、`while`、メモリ管理方式を、そのまま模倣することは前提にしない。
- 実用的なプログラムを試作し、違和感を添削することで仕様を発見・改善する。
- メモリ管理では **GCを前提とせず、Rust型のownershipシステムも採用しない方針**。ただし安全性・解放規則・寿命管理の代替案は未解決。

## 2. 基本文法

### 2.1 基本規則の方向性（合意した方針）

少数の共通規則を組み合わせる。

| 要素 | 現時点の扱い |
| --- | --- |
| `name[...]` | 名前と角括弧による構造 |
| `name{...}` | 名前と波括弧による構造 |
| `name(...)` | 名前と丸括弧による構造 |
| `:` | 名前・値などの対応関係 |
| `,` | 複数要素の区切り |
| 入れ子 | 上記の構造を再帰的に組み合わせられる |

括弧ごとの**厳密な意味・型付け・評価規則は未確定**。以前の厳密な `Category[Operation{Argument}]` 三段階構造に、現在の全構文を限定するわけではない。

### 2.2 演算（採用方針）

順ポーランド記法（prefix notation）を用いる。

```similarity
+(a,b)
-(a,b)
*(a,b)
<=(a,b)
+(3,*(4,2))
```

比較演算子の名前・型・オーバーフロー時の規則などの詳細は別途定義が必要。

## 3. 関数と引数名

### 3.1 添削を通じて合意した形

```similarity
Func[
    let{fib},

    func_argument{
        func_fib:func_n(type:int)
    },

    fib{
        ...
    }
]
```

- `Func[...]`：関数を表す構文候補。
- `let{fib}`：`fib` の定義。
- `func_fib`：関数 `fib` のデフォルト引数名として議論したもの。
- `func_n`：引数名の変更先。
- `func_fib:func_n(type:int)`：変更前→変更後を明記し、`int` 型を付ける提案。
- `fib{...}`：関数の処理本体を表す候補。

初期案 `func_argument{n(type:int)}` は、**変更元の名前が分からず、衝突も懸念される**として添削された。

### 3.2 識別子と衝突（今回の合意）

- `Func`（カテゴリ）と `func_` で始まる引数関連の識別子を、コンパイラが区別できるようにする意図。
- 別々の関数でも、引数の変更先に同一の `func_n` を使って衝突するなら、**コンパイルエラー**とする。
- コンパイラが暗黙的にスコープを選択したり、勝手に改名したりして衝突を解消しない。
- この衝突規則の適用範囲（モジュール、別名、外部シンボル等）は未定義。

衝突例（エラーとなる意図）：

```similarity
Func[
    let{fib},
    func_argument{func_fib:func_n(type:int)},
    fib{...}
]

Func[
    let{add},
    func_argument{func_add:func_n(type:int)},
    add{...}
]
```

`func_n` が重複している。

## 4. 変数と条件分岐（構文候補）

### 4.1 変数

```similarity
Var[
    let{
        a(type:int,value:0),
        b(type:int,value:1),
        next(type:int,value:0),
        i(type:int,value:0)
    }
]
```

`Var`、`type:`、`value:` の具体的な意味論や型推論は正式確定していない。これはフィボナッチ生成の出発値を明示する例である。

### 4.2 条件分岐

```similarity
If[
    conditions{
        <=(func_n,1)
    },
    truth{
        return(func_n)
    },
    failure{
        ...
    }
]
```

`If`、`conditions`、`truth`、`failure` は読みやすさのための候補。戻り値・分岐ブロック・評価順序の正式仕様は未確定。

## 5. フィボナッチの試作から分かったこと

### 5.1 最初の再帰関数と意図のずれ

試作では次のような再帰式を書いた。

```similarity
fib{
    If[
        conditions{<=(func_n,1)},
        truth{return(func_n)},
        failure{
            return(
                +(
                    fib(-(func_n,1)),
                    fib(-(func_n,2))
                )
            )
        }
    ]
}
```

この式が意図していたのは、**外部から `fib(n)` を呼んだ場合に、n番目のフィボナッチ数を返す計算**。

しかし関数定義だけでは呼び出しが存在せず、数列が0から自動的に生成されるわけではない。さらに、`func_argument{...type:int}` という宣言自体は、0や1などの初期値を与えていない。

設計者が実際に求めていたのは、**プログラムの内部で0と1から開始し、`0, 1, 1, 2, 3, 5, ...` を順番に生成する処理**だった。

### 5.2 書き直し案（実行可能性未確認）

```similarity
Func[
    let{main},
    main_attrib{public},

    main{
        Var[
            let{
                a(type:int,value:0),
                b(type:int,value:1),
                next(type:int,value:0),
                i(type:int,value:0)
            }
        ],

        Explore[
            search_area{
                variable(a,b,next,i)
            },

            how_explore{
                print(a),

                assignment(next,+(a,b)),
                assignment(a,b),
                assignment(b,next),

                assignment(i,+(i,1))
            },

            check{
                >=(i,6)
            }
        ]
    }
]
```

想定出力：

```text
0
1
1
2
3
5
```

**注意：** これはアルゴリズムの意図を説明するための草案であり、`Explore` が「処理後に `check` を評価する」という仮定を置いている。実行順序・終了条件・作用域・`print` と `assignment` の仕様も未確定で、現行コンパイラで動作確認したコードではない。

添削からの教訓：

1. 関数の**定義**と**呼び出し**を区別する。
2. 「n番目の値を計算する」ことと「数列を順番に生成する」ことは別。
3. 初期状態（ここでは `a=0`、`b=1`）を明示する。
4. 理解に必要な暗黙の前提を勝手に補わない。

## 6. 反復・探索の抽象化

### 6.1 今回の方向性

当初の `While[...]` は既存のループ構文を模した提案だったが、**`Loop` は表現したい概念として狭すぎる**という指摘があった。

探索（`Explore`）という、より広い考え方で検討を進める。ただし単なる「whileの改名」にはしない。ループの具体的な方法をアルゴリズムとしてどう表現するかも含めて、構造を再検討する。

歴史的な案：

```similarity
Explore[
    search_area{...},
    how_explore{...},
    check{...}
]
```

これらの各フィールドは**正式仕様ではない**。探索対象、探索手順、判定条件、結果の受け渡し、反復処理の位置づけ、終了条件のタイミングを今後検討する。

## 7. メモリ管理の検討

### 7.1 目標

- 固定長データと可変長データの**混在**を自然に扱う。
- コンパイル時に分かるサイズ／レイアウトを有効利用する（ただし実アドレスまでコンパイル時に確定するとは限らない）。
- GCやRust型ownershipに頼らない。
- 使わないメモリ領域の大規模な事前予約は避けたい。
- 通常アクセスは可能な限り低コストにする。
- データ移動による長時間の停止、特にStop-the-Worldを避けたい。

### 7.2 物理配置の有力仮説（未採用）

サイズの安定性や成長傾向を参考に配置する考え方：

```text
[固定長][安定した可変長][時々成長][頻繁に成長][空き]
```

可変長は「サイズが確定したものから詰める」発想が出た。ただし、**一度サイズが決まった後に再成長するデータ**があることが課題。

一緒にアクセスされやすいデータの近接性、寿命、成長頻度・成長量の予測を配置の参考にする案もあるが、特徴量や予測手法は未確定。

### 7.3 成長時の相対配置とスライド

```text
Before: [A][B][C][D][E][free]
After:  [A][B + extension][C][D][E]
```

後続の論理的な開始位置を、直前の開始位置とサイズの関係で表す発想：

```text
C.start = B.start + B.size
D.start = C.start + C.size
E.start = D.start + D.size
```

ここでは各データの `start` を先頭アドレス、`size` を占有単位数とみなす。境界用の追加領域が必要なら別途加算する。

`B` の拡張量が確定すれば、新たな `C/D/E` の位置も求められる。ただし、**計算で位置が決まることと、実データが瞬時に移動することは違う**。

連続領域内で後続データを動かすなら、一般に末尾側から重なりを壊さず移動させる方法が考えられる。後続の総サイズが大きければ移動コストも大きくなる。

## 9. 次に検証したい事項

1. 簡単なプログラム（フィボナッチ、配列探索、データ追加・削除）を草案のSimilarityで書いて、文法の摩擦を確認する。
2. `Explore` が表す対象と、条件評価・終了処理・結果取得の意味を設計する。
3. 引数名の変更と衝突の扱いを、モジュール／複数関数／複数引数でも検証する。
4. メモリ管理案を実装して、移動バイト数、最大停止時間、アクセス速度、メモリ利用量、参照安全性を測る。
5. 草案を正式仕様へ昇格するときは、既存実装と差分を確認し、文法と意味論を別々に定義する。
